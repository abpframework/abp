# ABP Version 11.0 Migration Guide

This document is a guide for upgrading ABP v10.x solutions to ABP v11.0. There are some changes in this version that may affect your applications. Please read them carefully and apply the necessary changes to your application.

> **Package Version Changes:** Before upgrading, review the [Package Version Changes](../../package-version-changes.md) document to see version changes on dependent NuGet and NPM packages and align your project with ABP's internal package versions.

## Open-Source (Framework)

This version contains the following changes on the open-source side:

### Upgrade to .NET 11

ABP v11.0 targets .NET 11. Move your solution to .NET 11 before upgrading the ABP packages. .NET 11 is a Standard Term Support release.

See [What's new in .NET 11](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-11/overview) while you update the target framework and the ASP.NET Core, EF Core, and related package versions. The Blazor startup templates adopt the `BasePath` component. ABP also preserves the .NET 10 rounding behavior when `float` or `double` extra-property values are read as `decimal`.

### MVC UI Libraries

**Who is affected**

- Applications that reference `@abp/owl.carousel`, `OwlCarouselScriptContributor`, or `OwlCarouselStyleContributor`.
- Applications that reference `@abp/malihu-custom-scrollbar-plugin` or the Malihu scrollbar bundle contributors.
- Applications that call the `timeago` 1.x jQuery API directly. `@abp/timeago` now depends on `timeago.js` 4.x, and the bundled file is `/libs/timeago/timeago.full.min.js`.
- Applications that imported the `jquery-form` or `toastr` npm packages through an ABP package and do not reference them themselves.

**What changed**

- Owl Carousel is replaced by [Swiper](https://swiperjs.com/). The new packages are `@abp/swiper`, `SwiperScriptContributor`, and `SwiperStyleContributor`. `@abp/owl.carousel` and the Owl Carousel contributors are removed.
- The malihu custom scrollbar plugin is removed. The docs, feature management, and permission management pages use the browser scrollbar.
- `@abp/timeago` still contributes `TimeagoScriptContributor` and `abp.timeago.js`, and it loads `timeago.js` instead of the unmaintained `timeago` 1.x package.
- The unused `jquery-form` and `toastr` npm packages are no longer brought in by ABP. ABP toast notifications stay on ABP's own implementation.

**What to do**

- Replace Owl Carousel markup and initialization with Swiper if your pages called the Owl Carousel API.
- Remove malihu scrollbar initialization and any bundle contributor references.
- Review custom `timeago` calls against the [timeago.js](https://github.com/hustcc/timeago.js) 4.x API.
- Add your own `jquery-form` or `toastr` package reference if your pages still load those libraries.

> See [#26005](https://github.com/abpframework/abp/pull/26005), [#26000](https://github.com/abpframework/abp/pull/26000), [#26001](https://github.com/abpframework/abp/pull/26001), and [#26002](https://github.com/abpframework/abp/pull/26002).

### C# Client Proxies Generate Only Used Types

**Who is affected**

- Applications that regenerate C# client proxies and compile against generated contract types that are not reachable from an application service signature.

**What changed**

`CSharpServiceProxyGenerator` generates only the contract types reachable from service signatures. Types that are already referenced from the client project's assets are not generated again. Nested, generic, and same-named types that appear in signatures are still generated.

**What to do**

Reference the contract package, or keep a local type, for any DTO you use that the generator no longer emits. Regenerate the proxies after upgrading.

> See [#26205](https://github.com/abpframework/abp/pull/26205) for details.

### Blogging Module Uses SkiaSharp

**Who is affected**

- Applications that use SixLabors.ImageSharp in their own code without referencing it themselves, and get it through the Blogging module.

**What changed**

The Blogging module detects uploaded image formats with SkiaSharp (`SKCodec`) and no longer references `SixLabors.ImageSharp`.

**What to do**

Reference `SixLabors.ImageSharp` in the projects that use it.

> See [#26264](https://github.com/abpframework/abp/pull/26264) for details.

### Batch Permission Update

**Who is affected**

- Applications that implement `IPermissionManager` themselves, instead of deriving from `PermissionManager`.
- Applications that derive from `PermissionManager` and override `SetAsync(string, string, string, bool)`.

**What changed**

- `IPermissionManager` has a new `SetAsync(IEnumerable<KeyValuePair<string, bool>>, string, string)` member. It checks permission grants in a batch and updates only the permissions whose state changes.
- `PermissionAppService.UpdateAsync` calls the new overload once instead of calling the single-permission `SetAsync` in a loop. A derived `PermissionManager` that only overrides the single-permission overload still compiles, but the permission management UI no longer goes through it.

**What to do**

Implement the new member if you implement `IPermissionManager` yourself, and move the logic of an overridden single-permission `SetAsync` to the new overload.

> See [#26126](https://github.com/abpframework/abp/pull/26126) for details.

### Feature Value Update Skipped When Unchanged

**Who is affected**

- Applications that use MongoDB and handle `EntityUpdatedEventData<FeatureValue>`.

**What changed**

`FeatureManagementStore.SetAsync` does not update the feature value when the stored value already equals the requested one, so it no longer raises an entity updated event for it. The Entity Framework Core providers already behaved this way.

**What to do**

No action is required unless a handler of yours relies on receiving an event for a value that did not change.

> See [#26126](https://github.com/abpframework/abp/pull/26126) for details.

### Some EF Core Providers Have No EF Core 11 Release Yet

**Who is affected**

- Applications that use `Volo.Abp.EntityFrameworkCore.PostgreSql`, `Volo.Abp.EntityFrameworkCore.MySQL`, `Volo.Abp.EntityFrameworkCore.MySQL.Pomelo`, `Volo.Abp.EntityFrameworkCore.Oracle` or `Volo.Abp.EntityFrameworkCore.Oracle.Devart`.

**What changed**

ABP v11.0 uses EF Core 11. These database providers have no stable EF Core 11 release yet:

| ABP package | Provider version | Status |
| --- | --- | --- |
| `Volo.Abp.EntityFrameworkCore.PostgreSql` | `Npgsql.EntityFrameworkCore.PostgreSQL` 11.0.0-rc.3 | Works with EF Core 11.0.0. NuGet reports `NU1608`, because this version asks for EF Core 11.0.0-rc.3. |
| `Volo.Abp.EntityFrameworkCore.MySQL` | `MySql.EntityFrameworkCore` 11.0.0-preview | Preview release of the provider. |
| `Volo.Abp.EntityFrameworkCore.MySQL.Pomelo` | `Pomelo.EntityFrameworkCore.MySql` 9.0.0 | Fails with `MissingMethodException` when the `DbContext` is created. |
| `Volo.Abp.EntityFrameworkCore.Oracle` | `Oracle.EntityFrameworkCore` 10.23.26301 | Fails with `MissingMethodException` when the `DbContext` is created. |
| `Volo.Abp.EntityFrameworkCore.Oracle.Devart` | `Devart.Data.Oracle.EFCore` 11.2.192.10 | Fails with `TypeLoadException` when the `DbContext` is created. |

**What to do**

- PostgreSQL and MySQL applications can upgrade. ABP will move to the stable provider versions once they are released.
- Keep Oracle and Devart applications on ABP v10.x until the provider ships an EF Core 11 version.
- Pomelo 9.0.0 targets EF Core 9, so it doesn't work on ABP v10.x either.

### EF Core Tools No Longer Reference EF Core Design

**Who is affected**

- Applications whose migration startup project references `Microsoft.EntityFrameworkCore.Tools` but not `Microsoft.EntityFrameworkCore.Design`. Older startup templates added only `Microsoft.EntityFrameworkCore.Tools`.

**What changed**

`Microsoft.EntityFrameworkCore.Tools` 11.0 no longer depends on `Microsoft.EntityFrameworkCore.Design`. Without it, `dotnet ef` commands fail:

```
Your startup project 'Acme.BookStore.EntityFrameworkCore' doesn't reference Microsoft.EntityFrameworkCore.Design. This package is required for the Entity Framework Core Tools to work.
```

**What to do**

Add `Microsoft.EntityFrameworkCore.Design` to the migration startup project. If you pass `--startup-project`, add it to that project:

```xml
<PackageReference Include="Microsoft.EntityFrameworkCore.Design" Version="11.0.0">
  <PrivateAssets>all</PrivateAssets>
  <IncludeAssets>runtime; build; native; contentfiles; analyzers</IncludeAssets>
</PackageReference>
```

### Static Assets on .NET 11.0.1xx SDKs

**Who is affected**

- Applications that map static assets with `MapStaticAssets()` instead of `MapAbpStaticAssets()`.
- Web SDK class libraries that are built in Debug with a .NET 11.0.1xx SDK.

**What changed**

- The .NET 11.0.1xx SDKs give the compressed copies of package static assets duplicate labels. When two packages have a static asset with the same path, the application fails on startup with `The static asset '...' is already mapped`. `MapAbpStaticAssets()` adds the missing package base path to these labels, so static asset compression stays enabled.
- A Debug build of a Web SDK project also fails on these SDKs when it references a Web SDK class library. `Volo.Abp.AspNetCore` sets `EnableHotReloadInRuntimeConfigDevFile` to `false` in Web SDK class libraries in Debug builds.

**What to do**

No action is required if your application uses `MapAbpStaticAssets()`, as the startup templates do. If it calls `MapStaticAssets()` directly and fails with this error, use `MapAbpStaticAssets()` instead, or turn off static asset compression in the project:

```xml
<PropertyGroup>
  <CompressionEnabled>false</CompressionEnabled>
</PropertyGroup>
```

ABP will remove these workarounds once the SDK fixes the problems.

> See [dotnet/sdk#56891](https://github.com/dotnet/sdk/issues/56891) and [dotnet/sdk#56656](https://github.com/dotnet/sdk/issues/56656) for details.

### Polly Is No Longer Referenced

**Who is affected**

- Applications that use Polly in their own code without referencing the `Polly` package themselves, and get it through one of the ABP packages below.

**What changed**

- ABP retries its own HTTP requests and file operations with `Volo.Abp.Threading.RetryHelper`, so these packages no longer reference `Polly`:

| Package | Removed reference |
|---------|-------------------|
| Volo.Abp.BlobStoring.FileSystem | Polly |
| Volo.Abp.FeatureManagement.Domain | Polly |
| Volo.Abp.PermissionManagement.Domain | Polly |
| Volo.Abp.SettingManagement.Domain | Polly |

- The number of attempts, the delays between them and the failures that are retried are unchanged in all of them.
- File-system operations now also observe cancellation before an attempt and while waiting between attempts.

**What to do**

Reference the package in the projects that use it. `abp update` rewrites `Volo.*` references only, so it does not add this one. ABP referenced Polly 8.6.3 up to v10.7, so that version keeps the behavior you had:

```xml
<PackageReference Include="Polly" Version="8.6.3" />
```

`RetryHelper` is an alternative if you use Polly only to retry a failing call:

```csharp
using var response = await RetryHelper.ExecuteAsync(
    async cancellationToken => await httpClient.GetAsync(url, cancellationToken),
    new RetryOptions<HttpResponseMessage>
    {
        MaxRetryCount = 3,
        ShouldRetryOnResult = response => !response.IsSuccessStatusCode
    });

response.EnsureSuccessStatusCode();
```

### Docs Module Renders PDF Files with HtmlRenderer.PdfSharp

**Who is affected**

- Applications that use the PDF export of the Docs module and customize, replace or derive from `ITextHtmlToPdfRenderer`, for example to provide fonts through `GetFontProviderAsync`.
- Applications that set their own `HtmlStyle` in `DocsProjectPdfGeneratorOptions`, or export Chinese, Japanese or Korean documents.
- Applications that use iText in their own code without referencing it themselves, and get it through `Volo.Docs.Domain`.

**What changed**

- `Volo.Docs.Domain` no longer references the iText packages (`itext7`, `itext7.pdfhtml` and `itext.bouncy-castle-adapter`), which are licensed under AGPL. `ITextHtmlToPdfRenderer` and `HtmlIdTagWorkerFactory` are removed.
- `PdfSharpHtmlToPdfRenderer` is the new default `IHtmlToPdfRenderer`. It uses [HtmlRenderer.PdfSharp](https://www.nuget.org/packages/HtmlRenderer.PdfSharp) (BSD-3-Clause) and [PDFsharp](https://www.nuget.org/packages/PDFsharp) (MIT). It supports CSS 2 level styles, uses the fonts installed on the server and does not fall back to another font for a single missing character. GIF and WebP images are converted to PNG with SkiaSharp, and SVG images are rendered as links.
- The default `HtmlStyle` no longer sets `width: 100%` on table cells, wraps long lines in code blocks, and adds the Liberation and DejaVu fonts as fallbacks for Linux servers.

**What to do**

- Move your `ITextHtmlToPdfRenderer` customizations to `PdfSharpHtmlToPdfRenderer`, or implement `IHtmlToPdfRenderer` yourself to keep using another engine. `PdfSharpHtmlToPdfRenderer` uses HtmlRenderer types in its virtual methods, and `Volo.Docs.Domain` does not expose them to your project, so add a `HtmlRenderer.PdfSharp` package reference to the project that derives from it.
- Install fonts on Linux servers and containers, for example the `fonts-dejavu-core` or `fonts-liberation` package. Otherwise the text is rendered with HtmlRenderer's built-in fallback font.
- Add the `SkiaSharp.NativeAssets.Linux.NoDependencies` package to your host project on Linux, so GIF and WebP images can be converted. The `SkiaSharp.NativeAssets.Linux` package loads fontconfig and can crash the process on servers where fontconfig is installed.
- If your application sets its own PDFsharp font resolver (`GlobalFontSettings.FontResolver`), replace `IHtmlToPdfRenderer`. HtmlRenderer.PdfSharp sets its own global font resolver, and PDFsharp does not allow changing it once it is used.
- For Chinese, Japanese or Korean documents, install a TrueType (`.ttf`) font that contains both Latin and these characters and put it first in the `font-family` of `HtmlStyle`, as explained in the [Docs module](../../modules/docs.md#generating-pdf-files) document. Font collections (`.ttc`) are not loaded.
- If you replace `HtmlStyle`, do not rely on flexbox or grid layouts, and generate a PDF to check your tables and code blocks.
- Reference the iText packages in the projects that use them.

### Docs Module Uses the New Elasticsearch Client

**Who is affected**

- Applications that enable the full-text search of the Docs module with an Elasticsearch 7.x server.
- Applications that implement `IElasticClientProvider`, derive from `DefaultElasticClientProvider` or `ElasticDocumentFullSearch`, or call `DocsElasticSearchOptions.Authenticate`.
- Applications that use NEST in their own code without referencing it themselves, and get it through `Volo.Docs.Domain`.

**What changed**

- `Volo.Docs.Domain` uses `Elastic.Clients.Elasticsearch` 8.x instead of `NEST` 7.17.5, which is deprecated. The new client works with Elasticsearch 8.x and 9.x servers.
- `IElasticClientProvider.GetClient()` returns `ElasticsearchClient` instead of `IElasticClient`.
- `DocsElasticSearchOptions.Authenticate` takes and returns `ElasticsearchClientSettings` instead of `ConnectionSettings`. `UseBasicAuthentication` and `UseApiKeyAuthentication` are unchanged.
- `ElasticDocumentFullSearch.HandleError` takes `ElasticsearchResponse` instead of `IElasticsearchResponse`.
- The index name, the index mapping and the stored documents are unchanged, so an index created by a previous version keeps working.

**What to do**

- Upgrade Elasticsearch 7.x servers to 8.x or later.
- Update your implementations and derived classes to the new types. See [Migration guide: From NEST v7 to .NET Client v8](https://www.elastic.co/guide/en/elasticsearch/client/net-api/8.19/migration-guide.html) for the query API changes.
- Reference the `NEST` package in the projects that use it.

### Localization Dictionaries Are Built Per Culture

**Who is affected**

- Applications that derive from `JsonVirtualFileLocalizationResourceContributor` and change the culture or skip files in `CreateDictionaryFromFile` or `CreateDictionaryFromFileContent`.
- Applications that rely on an invalid localization JSON file to throw on the first localization call.

**What changed**

`JsonVirtualFileLocalizationResourceContributor` reads the culture of each file first and builds the dictionary of a culture only when that culture is requested. Before, it parsed all culture files of a resource on first use. So an invalid file may now throw only when its culture is requested.

**What to do**

In a derived contributor that changes the culture or skips files, override `GetCultureNameOrNull` and return `null`. It then parses all files as before.

> See [#26378](https://github.com/abpframework/abp/pull/26378) for details.

## Pro

This version contains the following changes on the PRO side:

### Polly Is No Longer Referenced

**Who is affected**

- Applications that use Polly in their own code without referencing the `Polly` package themselves, and get it through `Volo.Abp.LanguageManagement.Domain` or `Volo.Abp.TextTemplateManagement.Domain`.

**What changed**

- Both packages retry with `Volo.Abp.Threading.RetryHelper` instead of Polly and no longer reference it. The number of attempts, the delays between them and the failures that are retried are unchanged.

**What to do**

Reference the `Polly` package in the projects that use it, as described in the open-source section above.

### Account Pro Passkey Names

**Who is affected**

- Applications that derive from `Volo.Abp.Account.Public.Web.Areas.Account.Controllers.AccountController` or `Volo.Abp.Account.ProfileAppService`, replace them with a derived class, or construct them manually.
- Applications that override `AccountController.RegisterPasskey`, or call the `api/account/registerPasskey` endpoint from their own client code.

**What changed**

- Passkeys now store the AAGUID of the authenticator that created them, and a passkey without a name is shown with the name of its authenticator, such as Windows Hello or Google Password Manager. You can add or change the known authenticators with `AbpIdentityPasskeyOptions.KnownAuthenticators`.
- `AccountController` and `ProfileAppService` take the new `IdentityPasskeyAuthenticatorNameProvider` dependency.
- `AccountController.RegisterPasskey` returns the registered passkey as a `PasskeyDto` instead of returning nothing. Its `Name` is `null` when the authenticator is unknown.

**What to do**

Add the new parameter to your derived constructors and pass it to the base constructor. If you override `RegisterPasskey`, change its return type to `Task<PasskeyDto>`.

No database migration is needed. The AAGUID is stored inside the existing passkey data, and the passkeys registered before the upgrade have no AAGUID, so they keep showing as unnamed until the user renames them.

### Payment Amount Conversions

**Who is affected**

- Custom payment gateways and application code that convert Payment module prices from `float` to `decimal`.

**What changed**

Payment prices are still `float`. On .NET 11, converting `19.99f` directly to `decimal` returns `19.9899997711181640625m` instead of `19.99m`. This can change amounts sent to payment providers or compared with their responses. The built-in gateways already handle these conversions on .NET 11.

**What to do**

No action is needed if you only use the built-in gateways and don't convert these prices yourself. Otherwise, use `PaymentAmountHelper.ToDecimal(float)` from the `Volo.Payment.Domain` package when converting Payment prices to `decimal`:

```csharp
using Volo.Payment;

decimal unitPrice = PaymentAmountHelper.ToDecimal(product.UnitPrice);
decimal totalPrice = PaymentAmountHelper.ToDecimal(product.TotalPrice);
```

The helper rounds to seven significant digits, rather than a fixed number of decimal places. For your own decimal constants, use a decimal literal such as `19.99m` instead of `(decimal)19.99f`.
